# Automation Scenarios

자동화 시스템 시나리오 정의서

## 개요

BandAuto 자동화 시스템의 사용자 시나리오와 유스케이스를 정의합니다.

### 핵심 액터

| 액터 | 설명 |
|------|------|
| **사용자** | 소싱 앱을 사용하는 관리자/운영자 |
| **시스템(스케줄러)** | 자동 실행을 담당하는 cron 기반 백그라운드 서비스 |
| **외부 API** | Band API, AI API (Gemini/OpenAI) |

---

## 시나리오 목록

### 1. 초기 설정 시나리오

#### SC-001: 자동화 최초 설정
```
사용자 스토리: "처음 자동화를 설정하여 도매 게시물을 자동으로 수집하고 소매밴드에 발행하고 싶다"
```

**사전조건**
- 사용자 로그인 완료
- Band API 토큰 설정 완료 (SourcingApiConfig)
- AI API 키 설정 완료 (AiApiConfig)
- 최소 1개의 도매채널 등록 완료
- 최소 1개의 소매채널 등록 완료

**시나리오 흐름**
1. 사용자가 `/automation/settings` 페이지 접근
2. 수집 설정
   - 수집 대상 선택 (전체 채널 / 특정 채널 선택)
   - 수집 채널 ID 목록 선택
3. AI 변환 설정
   - AI 제공자 선택 (GEMINI / OPENAI)
   - 가격 정책 선택 (선택사항)
4. 발행 설정
   - 자동 발행 활성화 여부 선택
   - 발행 대상 소매채널 선택
5. 스케줄 설정
   - 실행 주기 선택 (1h / 3h / 6h / 12h / 24h)
6. 자동화 활성화 토글 ON
7. 설정 저장

**사후조건**
- AutomationConfig 레코드 생성/업데이트
- 스케줄러에 작업 등록
- nextRunAt 계산 및 저장

**예외 시나리오**
| 코드 | 상황 | 처리 |
|------|------|------|
| E001 | API 키 미설정 | "AI API 키를 먼저 설정해주세요" 안내 |
| E002 | 채널 미등록 | "수집할 채널을 먼저 등록해주세요" 안내 |
| E003 | 소매채널 미등록 | "발행할 소매채널을 등록해주세요" 안내 |

---

### 2. 수집 시나리오

#### SC-010: 수동 수집 실행
```
사용자 스토리: "지금 바로 도매채널에서 새 게시물을 수집하고 싶다"
```

**사전조건**
- 자동화 설정 완료
- 수집 대상 채널 존재

**시나리오 흐름**
1. 사용자가 대시보드에서 "수집 실행" 버튼 클릭
2. 시스템이 WorkflowLog 생성 (type: COLLECT, triggerType: MANUAL)
3. 설정된 채널별로 Band API 호출
4. 신규 게시물 식별 (externalId 기준 중복 체크)
5. 신규 게시물 Post 테이블에 저장
6. WorkflowLog 업데이트 (성공/실패 카운트)
7. 결과 토스트 메시지 표시

**사후조건**
- 신규 게시물 Post 테이블에 저장 (status: PENDING)
- WorkflowLog에 실행 이력 기록

**예외 시나리오**
| 코드 | 상황 | 처리 |
|------|------|------|
| E010 | Band API 토큰 만료 | 토큰 갱신 안내, 해당 채널 스킵 |
| E011 | Band API 오류 (500) | 해당 채널 스킵, 재시도 안내 |
| E012 | 전체 채널 실패 | FAILED 상태로 완료, 에러 메시지 표시 |

---

#### SC-011: 스케줄 자동 수집
```
시스템 스토리: "설정된 주기에 따라 자동으로 게시물을 수집한다"
```

**사전조건**
- AutomationConfig.isEnabled = true
- cronExpression 설정됨
- nextRunAt 시간 도달

**시나리오 흐름**
1. 스케줄러가 nextRunAt 시간에 작업 트리거
2. 시스템이 WorkflowLog 생성 (triggerType: SCHEDULED)
3. SC-010의 3~6 단계와 동일
4. nextRunAt 업데이트
5. lastRunAt 현재 시간으로 업데이트

**사후조건**
- 다음 실행 시간(nextRunAt) 갱신

---

### 3. AI 변환 시나리오

#### SC-020: 수동 변환 실행
```
사용자 스토리: "수집된 게시물을 AI로 분석하여 상품 정보로 변환하고 싶다"
```

**사전조건**
- 변환 대기 게시물 존재 (Post.status = PENDING)
- AI API 키 유효

**시나리오 흐름**
1. 사용자가 대시보드에서 "변환 실행" 버튼 클릭
2. 시스템이 WorkflowLog 생성 (type: TRANSFORM)
3. PENDING 상태의 Post 조회
4. 각 Post에 대해:
   - AI API 호출 (게시물 내용 → 상품 정보 추출)
   - 가격 정책 적용 (설정된 경우)
   - Product 레코드 생성
   - Post.status를 PROCESSED로 업데이트
5. WorkflowLog 업데이트

**사후조건**
- Product 테이블에 신규 상품 생성
- Post.status = PROCESSED
- Product.status = READY (발행 준비 완료)

**예외 시나리오**
| 코드 | 상황 | 처리 |
|------|------|------|
| E020 | AI API 할당량 초과 | 실패로 기록, 나머지 건 스킵 |
| E021 | AI 파싱 실패 | 해당 Post만 FAILED로 표시, 계속 진행 |
| E022 | 가격 계산 오류 | 기본 마진율 적용 |

---

#### SC-021: 개별 게시물 변환
```
사용자 스토리: "특정 게시물만 선택하여 변환하고 싶다"
```

**사전조건**
- 변환 대상 게시물 선택됨

**시나리오 흐름**
1. 사용자가 게시물 목록에서 특정 게시물 선택
2. "선택 변환" 버튼 클릭
3. postIds 배열로 executeTransformPipeline 호출
4. 선택된 게시물만 변환 수행

---

### 4. 발행 시나리오

#### SC-030: 수동 발행 실행
```
사용자 스토리: "준비된 상품을 소매밴드에 발행하고 싶다"
```

**사전조건**
- 발행 준비 상품 존재 (Product.status = READY)
- 소매채널 설정됨
- 소매밴드 API 토큰 유효

**시나리오 흐름**
1. 사용자가 대시보드에서 "발행 실행" 버튼 클릭
2. 시스템이 WorkflowLog 생성 (type: PUBLISH)
3. READY 상태의 Product 조회
4. 설정된 소매채널별로:
   - 중복 발행 체크 (PublishHistory)
   - Band API로 게시물 작성
   - 이미지 업로드 (구현 시)
   - PublishHistory 기록
   - Product.status를 PUBLISHED로 업데이트
5. WorkflowLog 업데이트

**사후조건**
- 소매밴드에 게시물 등록
- PublishHistory에 발행 이력 기록
- Product.status = PUBLISHED

**예외 시나리오**
| 코드 | 상황 | 처리 |
|------|------|------|
| E030 | 이미 발행됨 (중복) | 해당 상품-채널 조합 스킵 |
| E031 | Band API 발행 실패 | PublishHistory.status = FAILED, 에러 기록 |
| E032 | 이미지 업로드 실패 | 텍스트만 발행 또는 스킵 (설정에 따라) |

---

#### SC-031: 선택 상품 발행
```
사용자 스토리: "특정 상품만 선택하여 특정 채널에 발행하고 싶다"
```

**사전조건**
- 발행 대상 상품 선택됨
- 발행 대상 채널 선택됨

**시나리오 흐름**
1. 사용자가 상품 목록에서 특정 상품 선택
2. 발행 대상 채널 선택
3. "선택 발행" 버튼 클릭
4. productIds, channelIds로 executePublishPipeline 호출

---

### 5. 전체 파이프라인 시나리오

#### SC-040: 전체 자동화 실행
```
사용자 스토리: "수집부터 발행까지 한 번에 실행하고 싶다"
```

**사전조건**
- 자동화 설정 완료
- autoPublish = true (발행까지 진행하려면)

**시나리오 흐름**
1. 사용자가 "전체 실행" 버튼 클릭 또는 스케줄러 트리거
2. 시스템이 WorkflowLog 생성 (type: FULL_PIPELINE)
3. **Step 1: 수집**
   - SC-010의 3~5 단계 실행
   - 진행 상황 업데이트
4. **Step 2: 변환**
   - SC-020의 3~4 단계 실행
   - 진행 상황 업데이트
5. **Step 3: 발행** (autoPublish = true인 경우)
   - SC-030의 3~4 단계 실행
   - 진행 상황 업데이트
6. 전체 결과 집계
7. WorkflowLog 최종 업데이트

**사후조건**
- 3단계 모두 완료
- 최종 상태: COMPLETED / PARTIAL_SUCCESS / FAILED

**상태 결정 로직**
| 조건 | 최종 상태 |
|------|----------|
| failedCount = 0 | COMPLETED |
| successCount > 0 && failedCount > 0 | PARTIAL_SUCCESS |
| successCount = 0 | FAILED |

```
사용자 스토리: "자동화 실행 이력을 확인하고 싶다"
```

#### SC-051: 대시보드 통계 확인
```
사용자 스토리: "현재 자동화 상태를 한눈에 파악하고 싶다"
```

**시나리오 흐름**
1. 사용자가 `/automation/dashboard` 접근
2. 헤더 통계 표시
   - 오늘 수집된 게시물 수
   - AI 변환 대기 수
   - 발행 준비 상품 수
   - 오늘 발행 완료 수
3. 최근 실행 로그 표시
4. 다음 예정 실행 시간 표시

## 시나리오 흐름도

### 전체 자동화 파이프라인

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   수집       │     │   변환       │     │   발행       │
│  (Collect)  │────▶│ (Transform) │────▶│  (Publish)  │
└─────────────┘     └─────────────┘     └─────────────┘
      │                   │                   │
      ▼                   ▼                   ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│    Post     │     │   Product   │     │ PublishHistory│
│ (PENDING)   │     │  (READY)    │     │  (SUCCESS)  │
└─────────────┘     └─────────────┘     └─────────────┘
```

### 상태 전이도

```
게시물(Post) 상태:
PENDING ──(AI변환성공)──▶ PROCESSED ──(발행)──▶ (연결된 상품 상태로 관리)
   │
   └──(AI변환실패)──▶ FAILED

상품(Product) 상태:
DRAFT ──(AI변환완료)──▶ READY ──(발행완료)──▶ PUBLISHED
   │                      │
   └─────────────────────└──(발행실패)──▶ (READY 유지, 재시도 가능)

발행이력(PublishHistory) 상태:
SUCCESS: 발행 완료
FAILED: 발행 실패 (재시도 가능)
```

## 테스트 시나리오

### TC-001: 정상 수집 테스트
```
Given: 도매채널에 새 게시물 5개 존재
When: 수집 실행
Then: 5개 게시물이 Post 테이블에 저장됨
      WorkflowLog.successCount = 5
```

### TC-002: 중복 수집 방지 테스트
```
Given: 이미 수집된 게시물 3개 존재
When: 같은 채널에서 수집 실행
Then: 기존 3개는 스킵, 신규만 저장
      details.totalDuplicates = 3
```

### TC-003: AI 변환 실패 복구 테스트
```
Given: Post 5개 중 1개가 AI 변환 실패
When: 변환 재실행
Then: 실패한 1개만 재시도됨
      (FAILED 상태인 Post만 대상)
```

### TC-004: 중복 발행 방지 테스트
```
Given: Product A가 채널 1에 이미 발행됨
When: 같은 조합으로 발행 시도
Then: PublishHistory 유니크 제약으로 스킵
      에러 없이 다음 건 진행
```
